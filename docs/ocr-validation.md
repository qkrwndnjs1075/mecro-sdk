# OCR 모델과 검증

## 현재 처리

브라우저에 포함된 local-captcha-solver의 캡챠 전용 ONNX 모델을 ONNX Runtime Web의 WASM으로 실행한다. 모델·설정·런타임은 모두 확장에 포함하며 외부 OCR 서비스로 이미지를 보내지 않는다. 모델과 코드 출처는 [배포 고지](../extension/vendor/ocr/NOTICE.md), 재빌드 방법은 [OCR 빌드](../tools/ocr-build/README.md)에 있다.

원본 색상 이미지를 모델 규격의 BGR 텐서로 변환한다. 이전 Tesseract용 이진화·색상 군집·선 제거·획 복구는 적용하지 않는다. 모델 추론 결과는 공통 `recognizeImage`에서 앞뒤 공백을 제거하고 대문자로 통일한다. 영문·숫자 여부는 원래 인식 문자열로 검사한다.

자동 처리와 수동 미리보기 모두 같은 모델 생성 함수와 정규화 함수를 사용한다. 자동 요청의 직렬화·오래된 응답 거부는 `ocr-queue.js`가 소유하며, `offscreen.js`는 이 핸들러를 Chrome 메시지에 연결한다. 이미 시작한 처리는 완료될 수 있지만 오래된 결과는 입력에 사용하지 않는다. 직접 입력한 값은 덮어쓰지 않는다.

## 검증 결과

2026-11-19 새 배포 코드로 아래 결과를 확인했다.

- 회귀 표본 14개: 대문자로 통일한 정답과 자동 입력 전달값 모두 일치.
- 별도 합성 스트레스 표본 18개: 모두 일치. 이전 Tesseract의 잔여 실패 6개 포함.
- 실제 ONNX `InferenceSession.run`을 계측한 회귀 표본은 각각 추론 1회. 빈 이미지도 1회 추론 후 빈 결과로 반환한다. 이미지 source 자체가 없으면 추론하지 않는다.
- 큐·취소 8개 시나리오, DOM 입력 보호, background 메시지 라우팅 검사 통과. 큐 대역이 소문자 혼합 결과를 반환해도 자동 응답과 미리보기 후보는 대문자로 전달되는지 확인했다.
- 설치된 확장을 새로고침한 뒤 실제 offscreen 경로에서 보존 원본 세 개가 각각 `MRBDEA`, `EQKDDE`, `SXEERM`을 반환했다. 실제 사이트의 입력값 변경·제출·서버 인증 성공을 검증한 것은 아니다.

회귀에는 원본 data URL 3개, 스크린샷 7개, 합성 이미지 3개와 빈 이미지가 포함된다. 확대된 동일 문자열과 합성 표본이 섞여 있으므로 독립적인 실사용 정확도 추정이 아니다. 대소문자를 구분해야 하는 다른 용도에는 대문자 정규화 계약을 그대로 적용하지 않는다.

## 재현 방법

프로젝트 루트에서 `python3 -m http.server 18770 --bind 127.0.0.1`을 실행한다.

- `/tools/ocr-regression.html`: 실제 배포 모델, 대문자 결과, 자동 입력 전달값, 추론 횟수.
- `/tools/ocr-stress.html`: 합성 표본별 원문·기대값·일치 여부. 보고서의 `done`은 정답률과 별개다.
- `/tools/offscreen-queue-regression.html`: 실제 메시지 핸들러와 미리보기 큐, 제어 가능한 OCR 대역으로 취소·직렬화·오류 복구 확인.
- `/tools/capture-input-regression.html`: 실제 DOM 구조에서 입력 이벤트, 수동 입력 보호, 자동 제출, 오답 새 문자 요청, 재인식을 확인한다. Chrome 메시지는 대역이다.
- `/tools/background-routing-regression.html`: offscreen 전용 메시지와 일반 상태 메시지의 처리 책임 확인.

## 남은 범위

자동 처리와 미리보기는 모델 설정과 결과 처리를 공유하지만 각자 실행 인스턴스를 유지한다. 따라서 미리보기를 함께 열면 별도 요청이 생길 수 있다. 요청당 추론 1회와 화면 이미지당 전체 실행 1회는 다른 조건이며, 실행 통합은 별도 생명주기 검증이 필요한 후속 과제다.

confidence는 후보 모델의 점수이며 정답 확률로 보장하지 않는다. 이번에는 사용자가 요청한 대문자 변환만 적용했으며 길이를 자르거나 특정 문자열을 보정하지 않았다. 원본에서 실패가 추가되면 그 원본과 정답을 보존하고 기존 표본을 함께 검증한다.

## 이전 Tesseract 검증 기록

아래 내용은 교체 전 구현의 조사·실험 이력이다. 현재 배포 동작은 위 설명을 기준으로 한다.

### 당시 Tesseract 인식 방식

자동 처리와 수동 미리보기는 `recognize-image.js`에서 전처리 이미지를 한 번 인식한다. 전처리는 다른 색 선에 끊긴 획을 복구하고, 문자 영역 높이보다 긴 연속 가로 구간에서 위아래 획이 없는 가장자리 픽셀을 제거한다. `ocr-worker.js`가 단일 문자열 처리 모드(`SINGLE_WORD`)를 설정한다. 결과가 비어 있지 않은 영문·숫자 문자열이면 입력에 사용한다. 두 크기 인식·후보 일치 검사·confidence 비교는 사용하지 않는다. 전경이 없는 이미지는 OCR을 호출하지 않으며, 처리 도중 요청이 바뀌면 이전 결과를 버린다. 아래의 1차·2차 수정 및 설치 확장 확인은 이전 방식의 검증 이력이다.

### 원본에서 재현한 글자 추가 오류와 처리 결과

`extra-letter-original.json`은 실패한 페이지에서 확보한 210×70 원본이다. 수정 전 `EQKDDE`를 `EQKDBDE`로 읽었다. OCR 문자 좌표에서 한 `D` 영역에 `D`와 `B`가 겹쳐 배정됐다. 분할 모드만 바꾸면 이 표본은 해결되지만 기존 같은 색 선 표본의 `CDRWDD`가 `CDRWDHD`로 바뀌었다. 따라서 공통 전처리에서 글자 사이 가로 연결을 제거하고 단일 문자열 모드를 함께 적용했다. 고정밀 float 모델, 사전 비활성화, 크기 변경은 두 표본의 상충을 해결하지 못해 적용하지 않았다.

2026-11-19 최종 코드로 회귀 표본 14개, 큐·취소 8개 시나리오, DOM 입력 및 백그라운드 메시지 라우팅 검사를 통과했다. 설치 확장을 새로고침한 뒤 실제 offscreen 워커에 보존 원본을 전달해 `{text: 'EQKDDE'}`를 확인했다. 이 검증은 실제 캡챠 입력값 수정·제출이나 서버 인증 성공을 포함하지 않는다.

| 발견 사항 | 처리 |
| --- | --- |
| 원본의 중복 글자 및 같은 색 선의 오인식 | 공통 전처리와 워커 설정을 수정하고 실패 원본을 회귀 검사에 추가 |
| 미리보기에서 잘못 읽은 기호를 지워 표시 | 앞뒤 공백만 제거해 후보를 그대로 표시하도록 수정 |
| background가 offscreen 대상 메시지에 잘못 응답 | 대상 메시지를 무시하도록 라우팅 경계를 수정하고 회귀 검사 추가 |
| 단일 인식 이후 남은 미사용 원본/복구 이미지 복제 | 내부 마스크를 하나로 정리 |
| 자동 처리와 미리보기의 별도 워커 실행 | 후속 추적. 이번 자동 처리 실패의 원인은 아니며, 실행 통합은 요청 취소·페이지 이동·미리보기 생명주기 검증이 필요 |
| 글자 수나 confidence로 정답 판정 | 적용하지 않음. 페이지 입력에는 길이 제약이 없고 confidence는 정답 보장이 아님 |

`tools/ocr-stress.html`은 수정 조건을 정한 후 생성한 18개 합성 표본의 한계 보고서다. Arial·Georgia·monospace, 선 없음·같은 색 선·다른 색 선, 1배·2배 조건을 사용한다. 비교 시 기존 7개 정답은 모두 유지됐고 수정 후 12개가 정답이었다. 아래 6개 실패는 후속 과제로 남기며, 보고서 완료(`done`)를 전체 정답으로 취급하지 않는다. 합성 표본 결과는 실제 캡챠 분포의 정확도 추정이 아니다.

### 이전 기울어진 선 수정 이력

2026-11-19 기울어진 방해선의 두께 판정을 수정했다. 선 전체의 바운딩 박스 높이 대신 픽셀 면적을 가로 폭으로 나눈 평균 세로 두께를 사용한다. 첨부 스크린샷의 선은 폭 333px·높이 19px·면적 760px로, 이전 높이 기준에서는 복구 대상에서 빠졌다. 같은 입력·OCR 설정으로 수정 전 `KAECLR`, 수정 후 `KAECLB`를 확인했다. 연결 영역 간 복구 조건과 OCR 1회 실행은 유지한다.

해당 스크린샷의 이미지 부분을 `sloped-line.json`으로 보존했다. 기존 12개 표본과 새 표본을 합친 13개, 큐·취소 8개 시나리오, DOM 입력 회귀가 통과했다. 새 표본은 화면에서 잘라낸 이미지이며 실제 원본 data URL이나 설치 확장의 동작을 검증한 것은 아니다. 평균 두께 판정도 휴리스틱이므로 복잡한 선·배경의 일반 정확도를 보장하지 않는다.

### 원인과 수정

밝기 이진화는 색이 다른 가로선과 문자를 같은 전경으로 합칠 수 있다. 가장자리 투표는 이미지 테두리나 스크린샷 여백을 배경으로 오판할 수 있다. 색상 군집을 단순 면적으로 선택하면 안티앨리어싱 윤곽·잡음이 글자 내부 대신 선택된다.

RGB 색상 군집화로 색 정보를 보존하고 최대 면적 군집을 배경으로 본다. 나머지 군집마다 작은 연결 영역을 제거하고 글자 높이를 가진 영역의 면적을 비교한다. 얇고 넓은 선은 이 점수에 포함하지 않는다. 선택한 마스크를 검은 글자와 흰 배경으로 변환해 OCR에 전달한다. 결과는 검증된 정답이 아닌 인식 후보로 표시한다.

### 재현

프로젝트 루트에서 `python3 -m http.server 18770 --bind 127.0.0.1` 실행 후 Chrome으로 `http://127.0.0.1:18770/tools/ocr-regression.html`을 연다. 스크린샷에서 추출한 이미지 7개, 원본 data URL 3개, 다른 색 조합의 합성 이미지 3개와 빈 이미지 1개를 실제 번들 OCR 엔진과 운영 워커 설정으로 검증한다. 문자 표본은 자동 입력에 전달할 문자열이 정답과 같고 OCR 호출이 1회여야 한다. 빈 이미지는 호출이 0회이고 결과와 자동 입력값이 비어 있어야 한다. 완료되면 `document.body.dataset.result`가 `pass`여야 한다. 실제 페이지 입력·이벤트는 별도의 입력 회귀 검사에서 확인한다.

### 이전 후보 비교 방식의 검증 이력

추가로 `letter-confusion.json`에는 스크린샷이 아닌 원본 data URL 표본을 저장했다. 기존 단일 크기 인식은 MRBDEA를 MREDEA로 읽었다. 모드 변경, 사전 비활성화, 세로 획 연결은 이 표본을 해결하지 못했으며 일부 틀린 결과도 높은 confidence를 반환했다. 기존 크기와 75% 크기에서 인식한 후보 중 비어 있지 않고 엔진 confidence가 높은 쪽을 선택하도록 `recognize-image.js`에 통합했다. 자동 워커와 수동 미리보기가 같은 함수를 사용한다. 이 비율은 현재 표본에서 확인한 경험적 설정이며 보편적 최적값이나 정답 보장이 아니다. 완료되는 인식 호출은 이미지당 2회이며 워커는 재사용한다. 당시 신규 원본을 포함한 8개 회귀 표본에서 후보 문자열만 검증했고, 후보 불일치에 따른 자동 입력 보류는 검사하지 않았다. 아래 수정에서는 이 검증 누락도 보완했다. 독립적인 랜덤 표본 정확도는 여전히 미측정이다.

기존 밝기 처리: 이전 표본 1배 BLKPKU / 2배 s ur, 새 표본 1배 빈 결과 / 2배 JN. 색상·연결 영역 처리 후 네 경우 모두 기대 문자열과 일치했다. 스크린샷에서 추출한 이미지이므로 실제 원본 data URL의 sd15 결과를 정확히 재현한 것은 아니다.

### 한계 및 후속 검증

픽스처는 수정에 사용한 회귀 표본으로 랜덤 캡챠 정확도의 추정 자료가 아니다. 별도 랜덤 원본 이미지와 정답으로 측정해야 한다. 배경이 최대 면적이고 문자색이 일관적인 경우를 대상으로 하며, 다색 문자·동일색 방해선·복잡한 배경에서는 실패할 수 있다. 인증 제출이나 서버 보안을 검증하지 않았다.

### 1차 수정: 문자 크기 정규화 및 처리 시간 개선

첨부 스크린샷의 글자 영역(352×118)을 잘라 `same-color-line.png`로 추가했다. 기존 전처리에서 첫 인식은 `CDRWDED`(confidence 47), 75% 크기는 `CDRWDD`(64)였다. 기존 최종 후보는 올바른 문자열을 골랐지만 두 결과가 달라 자동 입력은 보류했다. 이는 첨부 화면의 잘못된 첫 후보를 재현한 것이며, 당시 설치 확장이 왜 그 값을 입력했는지는 확인하지 않았다.

이미지 전체 높이로 확대하던 처리를 전경 영역의 경계로 자른 뒤 높이 48px, 사방 여백 10px로 정규화하도록 변경했다. 같은 배경 크기에서도 문자 크기가 달라지는 영향을 줄이고 불필요한 빈 픽셀 처리를 줄인다. 40px에서는 기존 합성 표본 하나의 두 후보가 불일치했다. 48px은 당시 9개 회귀 표본에서 확인한 경험적 설정이며 보편적인 최적값은 아니다. 이 단계에서는 방해선 자체를 완전히 제거하거나 손상된 획을 복원하는 알고리즘을 추가하지 않았다.

색상 군집 계산은 모든 픽셀을 매번 순회하는 대신 정확히 같은 RGB 색과 빈도를 묶어 가중 평균을 계산한다. 색을 양자화하지 않으며 군집의 출현 빈도와 초기 선택 순서를 보존한다. 크기 정규화 조건을 고정한 비교에서 이미지 픽스처 6개의 출력 픽셀이 기존 군집 처리와 일치했다.

2026-11-18 macOS Aside(Chromium 156)의 같은 페이지·워커에서 각 버전을 한 번 예열한 뒤 9개 표본을 5회씩 측정했다. 라운드마다 수정 전/후 실행 순서를 바꿨으며 시간은 이미지 읽기·전처리·두 번의 OCR을 포함하고 워커 초기화, 확장 메시지 및 실제 입력은 제외한다. 수정 전 기준은 이 작업 시작 시점의 미커밋 코드다.

| 지표 | 수정 전 | 수정 후 |
| --- | ---: | ---: |
| 전체 45회 처리 시간 중앙값 | 242.9ms | 164.5ms |
| 전처리 시간 중앙값 | 54.0ms | 25.9ms |
| 첨부 표본 5회 처리 시간 중앙값 | 300.5ms | 205.8ms |
| 최종 후보 문자열 정답 | 45/45 | 45/45 |
| 두 후보가 정답으로 일치하여 자동 입력 가능한 결과 | 35/45 | 45/45 |

처리 시간 중앙값은 약 32% 줄었다. 첨부 표본과 기존 B/E 혼동 표본의 후보 불일치가 해결됐으며 나머지 표본의 자동 입력 가능 결과를 유지했다. 같은 표본의 반복 측정이므로 45개의 독립 이미지에 대한 정확도가 아니다. 독립 원본 표본, 다른 기기 및 이번 수정본의 설치 확장 전체 지연은 미측정이다.

진행 중 이미지가 교체되거나 탭이 닫히면 첫 OCR 이후 두 번째 인식을 생략한다. 자동 처리와 수동 미리보기가 같은 취소 함수를 사용하며 이미 시작된 OCR 자체를 강제 종료하지는 않는다. 탭 해제 후 동일 키·세대 번호가 재사용돼도 이전 작업이 살아나지 않도록 요청 객체의 동일성으로 최신 여부를 판단한다.

브라우저에서 OCR 9개 표본, 큐·취소 10개 시나리오, 기존 DOM 입력 회귀 검사를 모두 통과했다. 큐 검사는 OCR 워커를 제어 가능한 대역으로 바꾸되 실제 전처리·인식 조정·메시지 리스너를 실행한다. 첫 인식 중 교체되는 시나리오는 수정 전 오래된 문자열을 반환하고 두 작업 합계 4회 인식했으며, 수정 후 오래된 응답은 `stale`이고 합계 3회만 인식한다. DOM 검사는 자동 시작, 입력 이벤트, 이미지 변경, 오래된 응답 거부, 수동 입력 보존, 숨김·교체된 입력칸, 제출하지 않음을 확인했다. 검사에 사용한 Chrome runtime은 대역이므로 설치 확장의 권한·메시지 연결을 새로 검증한 결과는 아니다.

후속 작업으로 수동 미리보기와 자동 처리의 별도 워커 통합을 추적한다. 현재 미리보기를 함께 열면 동일 이미지를 별도로 처리할 수 있다. 실패한 같은 세대 요청의 재시도도 별도 과제로 남긴다. 이 변경에서는 새로운 재시도 정책이나 워커 공유 구조를 도입하지 않았다.

### 2차 수정: 원본 이미지의 획 손상과 입력 보류

새 스크린샷에서 추출한 `crossing-line.png`는 기존 코드에서도 두 후보가 `SXEERM`으로 일치했다. 그러나 실제 페이지의 원본 210×70 data URL인 `crossing-original.json`에서는 `SXEECRM`(confidence 8)과 `SXEERM`(89)로 갈려 자동 입력이 보류됐다. 화면 확대와 재표본화를 거친 스크린샷으로 원본의 실패를 대신 검증할 수 없음을 확인했다.

다른 색 가로선을 제외하면서 문자 획도 함께 끊긴 것이 이 표본의 직접적인 원인이었다. 기존 연결 영역 분석에서 가로로 길고 얇은 선의 픽셀과 문자 영역 ID를 함께 보존한다. 같은 열의 서로 다른 문자 영역 사이가 그 선으로만 가려졌을 때 복구 후보를 만든다. 새 색이나 이미지별 문자 정답을 코드에 넣지 않았다.

복구 이미지를 두 크기에서 반복 인식하는 방식은 기존 B/E 표본을 `MRBDEA` / `MRBEBDEA`로 갈라지게 했다. 따라서 전처리 결과를 `{primary, alternate}`로 명시하고 첫 후보는 복구 이미지, 두 번째 후보는 **복구 전 마스크**의 75% 크기를 사용한다. 복구할 픽셀이 없으면 같은 캔버스를 재사용한다. 모든 11개 문자 표본에서 두 번째 후보의 원본 캔버스가 수정 전 출력과 픽셀 단위로 일치함을 확인했다. 동일 문자열일 때만 입력하는 조건과 최대 두 번의 OCR 호출은 유지한다.

수정 후 원본 표본의 두 후보가 모두 `SXEERM`이 됐고, 기존 문자 표본과 새 원본·스크린샷을 합친 11개가 통과했다. 빈 이미지 검사에서는 OCR이 `I`를 만드는 기존 문제도 재현했다. 전처리에 전경 픽셀이 없으면 빈 결과를 명시해 인식을 생략하도록 수정했으며, 후보와 자동 입력값이 비어 있어야 한다. 큐·취소 10개 시나리오 및 DOM 입력 회귀도 통과했다. 같은 워커로 11개 문자 표본을 3회씩 교차 측정한 전체 처리 시간 중앙값은 수정 전 217.3ms, 수정 후 214.3ms였고 전처리는 39.0ms, 41.2ms였다. 작은 시간 차이의 성능 개선을 주장하지 않는다.

설치 확장이 현재 `mecro-sdk/extension` 폴더를 사용하는 것을 확인한 뒤 확장 관리 화면에서 새로고침했다. 같은 원본 이미지가 남아 있는 실제 페이지에서 입력값이 빈 문자열에서 `SXEERM`으로 바뀌는 것을 확인했다. 직접 입력하거나 입력완료 버튼을 누르지 않았다. 화면에는 좌석 선택 10분 만료 팝업이 표시돼 있었으므로, 이 확인은 설치 확장의 OCR·메시지·입력값 반영까지이며 서버 인증 성공이나 예매 진행 성공을 뜻하지 않는다.

이 복구는 수직으로 이어질 획이 다른 색의 얇은 가로선에 가려진 경우의 휴리스틱이다. 대각선·같은 색 방해선·이미 연결된 윤곽의 일부 손상·제거된 작은 조각을 모두 해결하지 않는다. 두 후보는 같은 OCR 엔진을 사용하므로 독립적인 정확도 보증도 아니다. 신규 실패 원본은 보존하고 독립 표본 정확도는 계속 별도로 측정해야 한다.

### 자동 입력 검증

같은 서버의 `/tools/capture-input-regression.html`은 실제 DOM에서 자동 시작 요청, 입력값 및 input/change 이벤트, 이미지 변경 시 이전 자동값 제거, 오래된 결과 거부, 수동 입력 보호, 숨겨진 팝업 및 교체된 입력칸 보호, 제출 클릭 없음, 캐시 복원 후 재감지, 결과 탭 없는 자동 응답을 검증한다. 이 페이지의 Chrome runtime은 테스트 대역이다. 페이지 측에서 입력 직전 원본 이미지와 세대 번호를 다시 확인한다.

#### 설치 확장 검증과 실행 구조 수정

실제 설치 확장에서 비활성 결과 탭은 15초 이상 OCR 대기 상태였고 탭을 활성화하자 약 0.2초 뒤 입력됐다. 페이지 캐시 복원으로 포트가 끊기는 오류도 관찰했다. 자동 실행을 UI 탭과 포트 생명주기에 의존시킨 구조가 잘못됐다.

자동 처리는 [Chrome Offscreen API](https://developer.chrome.com/docs/extensions/reference/api/offscreen)의 WORKERS 용도로 실행하는 단일 숨겨진 문서로 옮겼다. 워커를 공유하고 요청을 직렬 처리하며 대기 중 같은 문서의 오래된 요청은 건너뛴다. 이미지 디코딩은 createImageBitmap을 사용한다. 수동 미리보기와 자동 처리의 워커 설정은 ocr-worker.js가 소유한다.

최신 요청 판단은 도착 순서가 아닌 페이지 관찰자 ID와 이미지 세대 번호를 사용한다. `/tools/offscreen-queue-regression.html`에서 새 요청이 먼저 도착한 경우, 늦게 도착한 중복 요청, 탭 종료 후 상태 정리를 확인한다. 이미지 교체가 빠르더라도 오래된 요청이 최신 작업을 취소할 수 없어야 한다.

이번 문자 크기·성능 수정 이전의 설치 확장 검증에서는 정상적으로 열린 허용 호스트 페이지에 검증용 DOM 팝업을 삽입했을 때, 추출 버튼이나 결과 탭 활성화 없이 약 1.4초 후 SRCNNS와 input 이벤트 수신을 확인했다. 완료 후 검증용 DOM을 제거했다. 이는 당시 실제 확장·권한·메시지·OCR·입력 연결을 검증한 것이며, 이번 수정본의 설치 상태나 서비스의 실제 캡챠 정답 제출, React 상태 반영을 검증한 것은 아니다. 당시 별도 새 페이지는 HTTP 403으로 검증에 사용하지 않았다.
